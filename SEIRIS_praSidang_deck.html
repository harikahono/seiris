Kenapa equity tim startup mahasiswa selalu berantakan?

P1

Bagi rata: populer tapi tak adil

45,9% tim 2 orang memilih bagi rata (naik dari 31,5%) — padahal satu anggota bisa kerja full-time sementara yang lain sibuk kuliah → porsi tak sebanding → kohesi tim menurun.

P2

Kontrak statis tak mengikuti perubahan

Kesepakatan porsi di awal gagal mengakomodasi perubahan kontribusi seiring waktu; fixed split menuntut prediksi masa depan yang sulit diprediksi tim baru.

P3

Spreadsheet rawan & tak bisa diaudit

Manipulasi histori + human error; nilai deal PM/Sales tak bisa diverifikasi (selisih yang dikomunikasikan vs dari klien) → erosi kepercayaan tim.

P4

Aplikasi komersial top-down

Tanpa voting komunal & verifikasi bukti (invoice), keputusan dijatuhkan dari atas → fraud internal tak termitigasi.

2 tantangan teknis: (1) lost update saat ≤8 aktor menginput / memicu kalkulasi ulang secara konkuren · (2) belum ada verifikasi komunal deterministik untuk mitigasi asimetri informasi & fraud internal.

Catatan S4 — FMR & Duit (kritik terberat)

Jawaban 1 menit FMR: FMR = nilai wajar 1 jam kerja anggota, seolah digaji pasar. Semua kontribusi dinormalisasi ke slice = nilai x pengali risiko. Porsi = slice kamu : total slice semua. Formula Slicing Pie Mike Moyer. Slice = alat ukur fiktif. Bukan uang/saham. Yang penting RATIO, bukan angka mutlak. Pie selalu 100% (zero-loss). Rumus per-scope (kalau ditanya "rumus per project & per tim?"): - Satu kontribusi: slice_i = nilai x multiplier. - Pie project (p): equity_p(i) = slice_p(i) / T_p, dgn T_p = Σ slice semua member di project itu. Scope hanya kontribusi APPROVED milik project tsb. - Pie tim (induk): equity_T(i) = slice_T(i) / T_T, dgn T_T = Σ slice seluruh project + kontribusi tim-level. Tim = agregat SEMUA project (aktif & frozen) — inilah zero-loss di level tim. - Contoh Kopi Nusantara jadi bukti: total pie tim 19.740.000 = penjumlahan seluruh project + tim-level. Contoh hitung cepat: A TIME 10 jam x 50rb = 1jt slice; B CASH 250rb x4 = 1jt; C IDEA 5 jam x 100rb = 1jt. Total 3jt -> masing-masing 33,33%. Kritik "FMR subjektif, app cuma CRUD": - SEIRIS = wasit, bukan pembuat aturan. Judgment manusia tetap di puncak (by design). - Yang diautomasi = PROSES + enforcement: FmrProposal (ajukan->owner approve->audit), slices immutable, no self-vote, bad-leaver otomatis, cap 150k 3 lapis enforcement. - Trust dipindah ke mayoritas (voting), bukan dihilangkan. Kecurangan jadi mahal & terdeteksi. - Multiplier x4/x2 = default Moyer, bukan turunan data: "tugas app membuat multiplier apapun jadi enforceable". Frame kemenangan: "SEIRIS membuat penilaian manusia dapat diaudit, konsisten, bebas-race. Formula dari Moyer, enforcement-nya yang dibangun di TA."

Catatan S6 — FSM & Tie-Breaker

Skrip 5-tuple (15 detik): FSM = M = (Q, Sigma, delta, q0, F). Q = {PENDING, APPROVED, REJECTED}. Sigma = {vote_approve, vote_reject}. q0 = PENDING. F = {APPROVED, REJECTED} (terminal). delta = tabel transisi: PENDING + vote_approve + approvePct > threshold -> APPROVED. Guard: status harus PENDING, bukan self-vote (403), bukan vote ganda (409), tim/project tidak frozen. Tabel seri (hafal): tim 3 = pemilih 2, bisa 1-1; tim 4 = 3 pemilih, tidak bisa; tim 5 = 4 pemilih, bisa 2-2; tim 6 = 5, tidak; tim 7 = 6, bisa 3-3. Trace 2-2 (T=50): approvePct 50 & rejectPct 50 -> keduanya GAGAL syarat strict > 50 -> BUKAN approved/rejected -> masuk tie-breaker. 2-2 TIDAK auto-reject di T=50. Di T=100, 1 reject = veto langsung. Tie-breaker: suara owner jadi penentu (bukan vote baru). Owner = pencatat -> fallback anggota terlama. Hasil -> audit tie_breaker_resolved + recalc. Jebakan "test tie-breaker-nya mana?": jujur: belum ada test otomatis, jalur diverifikasi manual lewat trace kode; rencana tambah test 2-2 sebelum sidang. JANGAN klaim teruji.

Catatan S8 — Concurrency & Stack

- lockForUpdate = SELECT FOR UPDATE (pessimistic row lock). Butuh PostgreSQL (SQLite no-op). - MVCC: PostgreSQL simpan multi-version tiap baris, baca konsisten tanpa blokir. - Isolation: READ COMMITTED + locking selektif, BUKAN SERIALIZABLE (performa). - Deadlock dicegah urutan kunci konsisten: tim -> kontribusi -> snapshot. - Lost update = anomali utama yang dicegah (2 vote bersamaan). - Rate limiter 3 lapis: api 120/mnt, write 30/mnt, auth 5/email + 60/IP. - Append-only ledger, BUKAN event sourcing/CQRS penuh — jangan overclaim. - Laravel Sanctum 2 mode: cookie (SPA) + bearer (mobile).

Catatan S9 — Testing

Jawaban 1 menit blackbox: uji perilaku via input->output tanpa lihat kode internal; EP = 1 wakil per partisi (efisien); BVA = nilai batas +-1 (bug di tepi). Angka REAL (pakai ini kalau ditanya): 108 skenario (71 BE + 37 FE), 100% pass. Jangan sebut angka tabel yang beda. BVA wajib hafal: amount 999/1000/1001; hours 0,4/0,5/744/745 (744 = 31 hari x 24 jam); commission_rate -1/0/100/101; password min 8; FMR 0-150.000. Kalau ditanya "kenapa EP/BVA?": validasi input lengkap & efisien; EP pilih 1 kasus per kelompok, BVA sasar garis batas karena bug cenderung di situ.
